# 常驻GPU执行器工程验收

本次只交付调度代码与工程验收，不恢复已归档的batch50正式实验，不重新标定，不调用LLM。所有历史终态、失败、账本、claim与归档保留。

## 调度接口

候选任务批量仍为50，物理网络形状仍为10行。两者与GPU并发数分离：

```json
{"population": 50, "gpu_execution": {"workers": 1}}
```

`gpu_execution.workers`支持1至5的整数，默认1。默认路径在教师GPU子进程的固定调用线程和当前stream串行执行10行单元，接近UG04冻结提交930db032的调度布局；50个候选保留各自配置和独立随机流。提高并发属于显式选择，不能由候选批量、方向数量或旧容量缓存自动升高。

并发大于1时，每个执行单元绑定一个常驻单线程执行器和一个固定stream。积分步之间、同一教师的多个配置之间持续复用；教师任务结束或异常时统一关闭。子stream先等待父stream的输入，输入登记到子stream；全部生产者结束后，返回张量登记到父stream，由缓存分配器保护父stream异步消费后的释放时机。排队工作在首个生产者失败后取消，在途工作全部收束，不再创建临时线程/stream组合。

`record_stream`的作用是管理存储生命周期，并不证明此前已经发生悬空访问。依据：[PyTorch 2.9生命周期约定](https://docs.pytorch.org/docs/2.9/generated/torch.Tensor.record_stream.html)。BLAS工作区按handle/stream组合保留，教师执行器结束后才统一清理；不在每步或每批次清理来伪造稳定平台。

## OOM接续

预实验和正式推理都由CPU协调器持有常驻教师GPU子进程。确认设备OOM后，原子进程写OOM回执和一次性接续授权，退出；协调器确认退出、回收进程后才创建新GPU进程，按50→40→20→10降低候选容量。若实际剩余批次更小，则直接下降至比实际批次更小的容量，不重复尝试相同有效批次。

接续绑定原配置、教师、条件、所有请求、原预留身份、注册表、manifest、账本哈希及OOM回执。新进程领取独占claim，不删除旧claim，不重复计费；已完成候选引用原测量，数值失败不重试。若OOM发生在终态已保存后的后处理阶段，则停止并保留产物，不重新采样。非OOM错误、内核崩溃及进程异常退出不会自动重启。

GPU子进程继承协调器已持有的执行锁，避免协调器意外退出后，在途GPU工作失去互斥保护。API密钥不传入GPU子进程。GPU进程的启动、PID、退出码、接续与关闭均保留审计。

## 连续资源验收

每教师验收8个连续批次，每批50候选、完整100积分区间；前2批预热，后6批同时检查：

- 所有逐步轨迹与独立10行参考逐位相同，外部随机流不变。
- 分配/保留显存的范围不超过预先声明的32MiB容差。
- BLAS及BLASLt工作区数量、ROCr队列事件引用计数、常驻线程池与stream数量保持平台。

另外执行真实双stream张量/VJP测试，父stream异步拼接后立即释放生产者张量并在子stream进行同形状分配，验证生命周期；连续8批、每批100轮。

工作区计数使用针对已安装PyTorch 2.9头文件编译的只读C++适配器，不使用硬编码容器偏移。队列指标通过已加载ROCr运行库的具名32位符号读取，并保存库哈希和语义：它是AQL队列事件的引用计数，不是累计提交的kernel数，也不是对全部驱动内部队列的枚举。计数不可获取时明确报告不可用，不能填写零并宣布验收通过。显存包含PyTorch分配/保留与设备可用量，不能把缓存统计等同于全部驱动显存。

连续批次通过只是本次有限观察，不能保证无限期运行或所有并发数都稳定。默认并发1的双教师验收与并发2的张量接口测试分别报告。完整100步通过一次不足以替代连续批次验收。
