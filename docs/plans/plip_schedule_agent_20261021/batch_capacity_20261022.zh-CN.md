## 进程管理方向

已实现 `adaptive_schedule/prefetch.py`，新默认配置使用 `interleaved_prefetch`；
旧冻结配置仍可走串行路径，不在原目录静默切换实现。
队列最多保存当前批和下一批的决策请求，生成及清理始终由单一前台执行者操作。
消费预取结果时再次核对完整历史和冻结总体统计的哈希，变化时拒绝生成。
已提交轮次续跑时仅补齐质量/清理事务；不会重新调用 Agent 或重复生成。

保持单一 GPU 推理所有者，LLM 请求使用独立的有界执行池；两教师批次交替进入就绪队列。
在一个教师等待 Agent 时，可以运行另一教师已经获得决策的 GPU 批次。
全局 LLM 并发上限仍为 4，不能两个教师各启动 4 个请求而无意翻倍。
每位教师独立维持完整 100 条链的轮次屏障和冻结总体统计；质量评价、最佳快照和清理提交后，才开放该批次的下一轮读取。
不允许两个线程同时修改共享模型的 `_adaptive` 或 integrator observer，也不在 GPU 工作进程等待网络时长期持有 GPU 执行权。

正式恢复前需给出两教师共用的容量/吞吐建议及随机一致性限制；本次测试结束后仍保持暂停。

## 容量结论与正式执行的边界

本次已选择物理推理批量100。容量脚本及梯度控制器已支持100；交替预取执行器目前仍按原20槽位历史/快照布局验收。
正式恢复前需要把100槽位的初态拼接、逐链父状态恢复、历史索引、质量评价和TOP1清理布局接入同一执行路径。
不能只将旧配置的`batch_size`改为100，也不能把通过容量测量表述为正式100槽位十轮优化已经运行。
该适配不以不同批量final一致为门槛；需要确保每条链的身份、恢复入口、实际RNG、评价和保留结果归属正确。
本次保留全部旧正式结果，不启动重跑或迁移。
